# 受限平台压缩（手机版）

把桌面版 KB 压到聊天应用可用，是体积、分块和召回三者同时受约束的问题。压缩的前提是“优先级高的知识一条不丢”，而不是把文件平均削小。

## 平台事实

这些数字来自实际运行反馈，随版本变化，执行前重新核对：

| 平台 | 限制 | 后果 |
| --- | --- | --- |
| Chatbox | 附件解析后约 20 MiB 上限 | 超限直接拒收；卡片太长会被分块，召回时读到半截 |
| Chatbox | 子块约 448 字符 | 单卡超过这个量级可能被切开，正文与索引脱节 |
| Tabbit | 单附件 20 MiB 上限 | 只接受 .json 附件，扩展名不对会被拦 |

结论：硬上限取 20,000,000 字节，留出安全余量后目标区间约 18.35–19.40 MB（UTF-8、未压缩、含 JSON 自身的 `size_budget.measured`）。

## 行长门禁

按行读取的工具（含应用端分块器）遇到超长物理行会截断。硬门禁：

- 每条物理行 UTF-8 字节数不超过 2048。
- 目录、证据表、章节表一行一条。
- 倒排索引 posting 和长数组按固定长度分块换行。
- 单张卡片序列化后不超过 420 字符。

别让一个 1 MB 的单行数组进交付文件——读取工具看不到它后面的内容。

## 精确字节预算

必须用真实序列化结果测量，不要用估算：

```text
bytes = Buffer.byteLength(serializedText, utf8)
```

`manifest.size_budget.measured` 会写进文件本身，所以测出来的是自引用结果。做法是迭代到不动点：先写占位值序列化，测量，再写入测量值重新序列化，重复几次直到字节数稳定（通常 2–3 轮收敛）。

体积判定包含三类：低于目标下限、落在区间内、超过硬上限。低于下限说明压过头了，要回退一部分内容。

## 预算阶梯

按顺序执行，每一步结束后重新测量；只有仍超目标才进入下一步：

1. 压缩重复解释：同一事实的冗余表述合并。
2. 合并近重复：同主语同类型同章节同时间、Jaccard 达阈值、无数字否定差异。
3. 删无引用归档卡：rank < 2 且没有任何卡片 refs 指向它。
4. 缩短时间线：非核心 timeline 卡正文压缩。
5. 合并同类阶段卡：同实体同时间同类型的阶段记录合并。

每一步都只动允许动的层。压缩到目标区间内就停，不要继续削。

## 禁删清单

以下内容任何一步都不得删除，只能降权或压缩表述：

- priority_rank 不低于 3 的卡片。
- 校准层（calibrated_supplements / calibrated_cards），逐字保留。
- 高风险标签卡。
- 人物阶段状态卡与冲突卡。
- 章节锚点、实体锚点、时间锚点（删了就会出现空索引）。
- 被其它卡片 refs 引用的卡片（删了会出现悬空引用）。

## 弱卡降权而非删除

占位、截断或只有名字的弱卡不要直接删：它们仍是有用的线索。给它们打“非实体性”标记（如 catalog 第 5 列 0），检索排序时降分，让正文卡排在前面。

判定“实体性”时看正文是否有实际事实内容，而不是看字段数量。只有名字和 ID 的卡就是弱卡。

## 手机版索引优化

手机端上下文更小、读取更粗，“一次命中”比桌面端更重要：

- 锚点限位：top-k 内最多一个锚点，锚点分数低于正文卡。
- 名字索引只收 CJK，结构词和占位名一律不进索引。
- 三套名字索引去重，避免同一实体重复投票。
- 前缀扩展覆盖 entities、aliases、keys，避免别名漏召回。
- 时间索引只收可归一化时间点，unknown 不进索引。

## 交付前门禁

```text
结构   JSON 可解析 / card_id 唯一 / refs 无悬空 / ev 下标有效
索引   七个索引均非空 / 无空 posting / 无悬空 posting
覆盖   每章节 / 每实体 / 每声明时间点都有锚点
检索   固定查询集 top-k 全命中，首命中是正文卡
行长   所有物理行 <= 2048 字节
卡长   所有卡片 <= 420 字符
体积   真实字节落在目标区间，未超硬上限
校准   calibrated 数据与源版逐字节一致
复现   同输入重跑得到逐字节相同输出
```

压缩后必须重跑完整回归。压缩最容易造成的故障不是文件损坏，而是“还能打开但查不到”，只有查询回归能发现它。

## 与桌面版的关系

两份 KB 共享同一套编号空间、字段语义和索引契约，差异只在体积策略。

- 桌面版是事实完整版，是手机版的唯一输入。
- 手机版不得反向作为事实来源。
- 两者 `manifest.prompt_compatibility` 必须一致。
- 生成手机版必须记录源桌面版的 SHA256，写入 manifest 以便追溯。
