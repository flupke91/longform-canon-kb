# 检索优化

这份文档来自一次真实的大型项目实测：48,387 张卡片、112 条固定回归查询、多轮应用端反馈。每条失败都真实发生过，处理顺序也验证过。

修检索问题先审计再动手，顺序固定：

```text
1. validate-kb     结构 / 引用 / 行长 / 体积
2. index-hygiene   冗余 / 噪音 / 重复 posting / 覆盖空洞
3. query-probe     真实查询回归，看 top-k 到底是谁
```

## 先证伪反馈，再改数据

应用端反馈是线索，不是结论。很多“KB 结构坏了”的报告其实是解析方式不对，改错方向会真把好数据改坏。先区分两类问题：

真问题：数据确实错（悬空引用、重复卡、字段错位、[object Object] 落盘）。

解析误解：数据没错，但读取方假设错了编号空间或编解码约定。

判定方法：拿反馈里的具体 ID 或章节号，按 references/kb-contract.md 的编号规则手算一遍，看是否自洽。自洽就是解析误解。

## 失败分类表

| 症状 | 真实根因 | 修复 |
| --- | --- | --- |
| “卡片引用全部悬空” | 读取方把 ch 字典下标当成章节号，或把锚点序号当卡片序号 | 走 chapter_catalog[ch][1]；走 mobile_card_catalog[ordinal][1] 取 ID；在 encoding 里把语义写死 |
| “ID 全对不上” | 用编号公式反推 card_id | 禁止公式反推，只从 catalog 取；公式只是构建器约定 |
| “章节 1218 查不到” | 章节字典下标不等于章节序号 | chapter_catalog 三列分离；查询先归一化 ch1218 再取 ordinal |
| “证据引用不到” | evidence 表缺失或类型词表漂移 | evidence 表必须与卡片一同发布；类型收敛为 Q/P/L/C/X |
| 卡片正文变成 [object Object] | 结构化时间字段被直接字符串化 | 序列化前归一化 story_time，对象按已知键展开，未知落 unknown |
| 人物性别或年龄错位 | 多字段数组按下标对齐，删除某项后整体移位 | 字段带键存储，不用位置对齐；构建期断言长度一致 |
| 精确人名查询前三位全是锚点 | 锚点卡与正文卡同分或被优先 | 锚点降权（约 -10 分）并限制 maxAnchors=1，正文卡优先 |
| 同一实体在多个索引重复投票 | entities / aliases / keys 三套索引含相同 posting | posting 完全相同时删 keys 项 |
| 查询命中一堆 record_type | 结构词进了名字索引 | 名字索引只收 CJK，过滤结构 token |
| 命中“未命名”“unknown” | 占位名未清洗 | 未命名*、unknown、空串、[object Object] 不索引 |
| 通用词命中无关卡 | 单字或通用词前缀扩展过宽 | 前缀扩展限制最短长度，通用词白名单外移；精确命中优先 |
| 别名搜不到 | 前缀扩展只扫 entities | 前缀展开覆盖 entities / aliases / keys |
| 时间查询返回空 | 时间未归一化，或 unknown 混进索引 | 时间索引只放可归一化值；保留 coverage_and_limits.time_anchors 声明 |
| 审计脚本统计证据类型全是 X | 类型词表漂移 | 固定五类码表，构建期校验 |
| 体积估算与磁盘不符 | 用字符数或估算代替真实序列化字节 | 用 Buffer.byteLength(serialized, utf8) 实测，并计入 size_budget.measured 自引用 |

## 修复决策表

按影响面从小到大做，每次只改一类，改完立刻跑回归：

| 改动 | 何时做 | 回归重点 |
| --- | --- | --- |
| 过滤噪音键 | 索引里出现结构词、占位名、[object Object] | 受影响的合法键仍能命中 |
| 去重复 posting | 多索引 posting 全等 | 实体查询命中数不变 |
| 锚点降权 | 锚点挤占 top-k | 精确人名首命中是正文卡 |
| 限制 maxAnchors | top-k 内锚点超过 1 | 章节查询仍能在 top-5 命中 |
| 前缀扩展补索引 | 别名查不到 | 别名与前缀用例全绿 |
| 归一化时间 | 时间字段是对象或 unknown | 时间锚点覆盖不减少 |
| 合并近重复 | 同主语同章节同时间、3-gram Jaccard 不低于 0.90 | 数字与否定差异不得被合并 |
| 删除无引用归档卡 | 体积超限且卡片 rank 低于 2 | 高优先级与依赖闭包完整 |

### 合并纪律

近重复合并只在同主语、同类型、同章节集合、同时间前提下进行，且必须排除：

- 数字差异（三元 对 五元）。
- 否定差异（可以 对 不可以）。
- 显式冲突声明。
- 冲突卡与校准卡本身。

3-gram Jaccard 不低于 0.90 是经验阈值。达到阈值但没有数字或否定差异才合并，否则保留双方。

## 查询回归

回归集要覆盖五组：核心设定查询、校准层查询、随机人物、随机章节、随机时间点。每条查询记录期望命中的 source_id 集合，判定标准是“top-k 里能通过 refs 一跳到达期望源”，而不是要求精确命中同一张卡。

判定顺序：

```text
1. 查询期望集非空（空期望本身就是故障）
2. top-k 至少一条命中
3. 首命中是正文卡，不是指针卡
4. 命中率不打折：裁剪前后同分
```

任何裁剪、去重、索引改动之后都必须重跑。没有回归的优化不算优化。

## 两类不能碰的数据

- 校准层：来自反馈的显式覆盖，逐字保留，压缩不得修改。
- 高优先级事实：priority_rank 不低于 3、高风险标签、人物阶段状态、冲突卡，以及它们的依赖闭包，永不被裁剪流程删除。

压缩只能降权或删除重复解释、脚手架和无引用归档。宁可文件大一点，也不要丢事实。
